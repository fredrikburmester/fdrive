## Recovery: trash and snapshot versions

Recovery uses ordinary upstream operations under each identity, never SFTPGo admin access or direct access to originals. Dedicated application metadata records ownership, provider, original virtual path, opaque item UUID, timestamps and operation state. Store recovery bytes in a dedicated identity-UUID namespace under a reserved `.fdrive` directory within the user's virtual home. Before enabling, verify the directory is absent or has a valid application ownership marker; an unrelated pre-existing directory is a conflict, never reused, hidden, overwritten or deleted. Persist the exact initialized recovery location. Never list/index/search that reserved area as ordinary user content; all recovery access goes through owned-identity endpoints. Do not silently choose another location when permissions deny recovery storage. Native upstream permission checks remain authoritative.

Trash is an explicit Move to Trash action with Restore and Delete Permanently in a Trash page. Preserve the existing explicit permanent-delete path and its confirmation; do not reinterpret API deletion as trash behind clients' backs. Restore refuses destination conflicts and offers an explicit new basename. No automatic expiration or emptying by default. Background operations have durable pending/ready/error state, recovery after process restart, bounded work and cancellation. Cross-system database/upstream steps require compensating or resumable actions; a failure must never lose the only copy. Restore metadata/tags/favorites through the existing rename machinery. Paths and descendants in recovery storage cannot become archive, sharing, indexing or Office bypasses.

Versions are file snapshots, explicitly created or enabled for fdrive writes. Existing snapshots follow renames. Snapshot and restore use native upstream copy/stream operations with bounded temporary storage; originals are replaced only after a complete snapshot/restore source is available. Original read access is required before exposing old versions. Restoring creates a safety snapshot of the current file, refuses conflicting active Office writes, then replaces it and publishes normal update events. History accurately describes its scope: snapshots made by fdrive, not a complete record of arbitrary external writes. No retention deletion without an explicit user setting/action. Pin exact write/lock semantics in a dedicated chunk before implementation; recovery must not weaken Office transaction or credential-provider binding guarantees.

## Similar images

Use an indexer-computed perceptual image hash independent of the deferred embedding model. A bounded, documented Hamming-distance threshold ranks candidates; identical SHA-256 remains a separate exact-duplicate signal. Supported decodable raster images only; bounded pixel/file input, EXIF orientation normalization, no remote fetches. Persist algorithm/version and dimensions. Scoped candidate retrieval, virtual mapping round trips and live read permission checks apply before results/thumbnails. UI offers comparison/reveal and explicit existing file actions; never automatically delete a near match. Include transformed/cropped/different-image fixtures and false-positive explanation. Measure candidate lookup on the performance fixture; no unbounded all-pairs scan per request.

## Second provider: WebDAV

Use WebDAV as the second credential-based storage adapter. This avoids introducing OAuth or cloud accounts during unattended work. Operators configure a fixed endpoint; unprivileged users cannot supply arbitrary credential destinations. Login/link credentials remain encrypted at rest and bound to provider UUID and immutable endpoint, with the same account/session ownership rules. Follow redirects only under an explicitly safe same-origin policy; never forward credentials across origins. Strict namespace-aware DAV XML parsing with body/entry limits, href origin/prefix validation and canonical segment-safe paths. Implement list/stat/Range read/write/mkdir/move/copy/delete via the StorageProvider port, preserving streaming and native errors. Verify against a disposable real DAV server, including Unicode/literal-percent names, denied permissions, redirects, traversal, cancellation and cross-identity same-path isolation.

Provider capabilities are explicit. SFTPGo public shares remain SFTPGo-specific; hide unavailable actions for WebDAV rather than proxying through another identity. Index features are unavailable without an explicitly configured trusted local mapping. Office support may use the common storage port only after its permission policy and stable registry mapping are satisfied; otherwise show download/preview with an accurate unavailable state. Existing SFTPGo behavior and deployment defaults remain intact. Exact provider catalog, credentials, routes and schema contracts must be specified before implementation; no second-provider worker assigned yet.
