# P5 credential/provider binding (queued security chunk)

Review found a preexisting boundary gap amplified by linked accounts: TokenSource re-mints identity A credentials through a lazy client pointed at current configured server B. Generic filesystem storage also uses that lazy client. Checking provider before a lazy call does not pin its destination; a connection change can retarget a token/password. Office's direct-client snapshot already prevents token forwarding during writes, but its TokenSource mint still needs repair.

## Fixed architecture

All identity-authenticated traffic uses immutable client snapshots bound to that identity's providers row. Resolve identity, provider, current connection; require exact provider type/baseURL match current configured connection. Then construct direct createSftpgoClient({baseUrl: provider.baseUrl, fetch}) and retain that client for operation lifetime. No credential-bearing call through lazy URL resolver. A request already started against old provider may finish there; it must never retarget to newly configured server. New operations after switch fail unavailable/reauth. No fallback to another provider for same username.

TokenSource receives mandatory async clientForIdentity(identityId) resolver (rather than shared lazy sftpgo). Even cache hits validate binding, not only mint. Mint decrypts only after successful provider resolution, logs no password/ciphertext, sends to pinned client. Retry on401 remains once with same identity; the retry may deny if current connection changed. prime stores identity-specific token only. No extra DB resolution inside office write transactions: office obtains token/client before write scope as today.

Auth/storage factory resolves async fixed identity client and creates SftpgoStorageProvider using that client and identity-bound TokenSource.withToken. Update principal resolver/API-token resolver interfaces to await factory. Generic file list/read/write/copy/delete, previews, ZIP/jobs use bound identity snapshot. Jobs capture provider and identity at enqueue; delayed execution never adopts new configured server. Shares chunk supplies fixed-base client already; verify it also uses repaired TokenSource.

Initial login/link verifyAccountCredentials snapshots current connection and calls direct clientForBaseUrl(baseUrl), verifies connection still matches before creating/priming identity/session. Do not send entered credentials to a URL selected after capture by lazy client. Existing lazy client may remain for setup/connection health where no stored identity credential involved; don't mass-delete unrelated adapters.

No new routes/contracts/dependencies. Own when assigned: auth token-source/service/index/api-token middleware & tests/fixtures, accounts/credentials.ts/types/tests, storage factory module, composition wiring and directly affected integration fixtures. Parent pins exact files before launch after shares API releases composition. Production files outside ownership need explicit extension.

Tests: two HTTP fixture servers with recorded sanitized call counts; provider switches before cached get, during mint, between binding and execution, and before retry. B must NEVER receive A's password/JWT or file mutation. A and B with same usernames/paths distinct. Native identity query and API-token requests obey same rule. Old in-flight client continues only to A; new request denies. No cached token returned on provider mismatch. Unit pure100/package thresholds; real integration and root gates after review.
